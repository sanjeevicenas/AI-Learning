D1

Agentic Architecture & Orchestration

The biggest slice of the exam. How autonomous agents loop, how a coordinator drives subagents, and how you make multi-step work reliable with the Claude Agent SDK.

EXAM DOMAIN 127% of examHigh priority
Task 1.1 · Agentic loops

The loop runs on stop_reason

DefinitionAn agentic loop sends a request to Claude and inspects stop_reason. If it's tool_use, you execute the requested tool(s), append the results to the conversation history, and loop again. If it's end_turn, the agent is done. The model decides the next tool from context — not a hard-coded decision tree.
A chef working through ticketsThe chef keeps cooking and calling for ingredients (tool_use) until the dish is plated (end_turn). You don't tell them "stop after 5 steps" — you watch for "service!", the real done-signal.
Anti-patterns the exam loves to test
Wrong stop signalsParsing natural-language ("looks done") · arbitrary iteration caps as the primary stop · checking for assistant text as a completion flag.
Right stop signalBranch on stop_reason: continue on tool_use, terminate on end_turn. Append every tool result back into history first.
Memory hookThe loop's heartbeat is stop_reason. tool_use = keep going, end_turn = stop. Never let the model's prose decide when it's finished.
Tasks 1.2 & 1.3 · Multi-agent orchestration

Coordinator + subagents (hub-and-spoke)

DefinitionA coordinator agent decomposes the task, decides which subagents to invoke, routes all communication, aggregates results, and handles errors. Subagents run with isolated context — they do not inherit the coordinator's history, so context must be passed explicitly in the prompt. Subagents are spawned with the Task tool, which requires Task in the coordinator's allowedTools.
A newsroom editor and reportersThe editor (coordinator) assigns beats, hands each reporter (subagent) their brief, and stitches the stories together. Reporters don't see each other's notebooks — the editor passes along anything they need.

Orchestration mechanics

  1. Coordinator analyzes the query & dynamically selects subagents (don't always run the full pipeline).
  2. Pass complete prior findings directly in each subagent's prompt (with source metadata).
  3. Spawn parallel subagents by emitting multiple Task calls in one response.
  4. Run iterative refinement: evaluate synthesis for gaps, re-delegate with targeted queries.
Tough Scenario (real sample question)

A research system covers only "visual arts" for the topic "creative industries" — missing music, writing, film. Logs show the coordinator split it into digital art / graphic design / photography.

Wrong blamePatch the search agent, synthesis agent, or relevance filters — they all executed their assigned scope correctly.
Root causeThe coordinator's decomposition was too narrow. Broaden task decomposition to cover all domains. Fix the assignment, not the workers.
AgentDefinitionEach subagent type has a description, system prompt, and tool restrictions — scope tools to the role.
Context never auto-inheritsPass prior findings (with source URLs, doc names, page numbers) directly in the prompt; use structured formats to keep content separate from metadata.
Coordinator prompts = goals, not scriptsSpecify research goals & quality criteria, not step-by-step procedures, so subagents can adapt.
Exam goldSpawn parallel subagents = multiple Task calls in a single response (not across turns). And the coordinator's allowedTools must include Task or it can't delegate at all.
Tasks 1.4 & 1.5 · Enforcement & hooks

When "the prompt says so" isn't good enough

DefinitionPrompt instructions have a non-zero failure rate — fine for guidance, unacceptable for rules with money or safety on the line. For deterministic compliance, use programmatic enforcement: prerequisite gates and Agent SDK hooks. A PostToolUse hook transforms tool results before the model sees them; a tool-call-interception hook blocks policy-violating actions before they run.
A turnstile, not a "please tap in" signA sign asks nicely (prompt). A turnstile physically won't let you through without a ticket (hook/prerequisite gate). For "verify identity before refund," you want the turnstile.

Where hooks earn their keep

  1. Prerequisite gate: block process_refund until get_customer returns a verified ID.
  2. Interception: block refunds over $500, redirect to human escalation.
  3. Normalization: a PostToolUse hook unifies messy formats (Unix vs ISO 8601 timestamps, numeric status codes) before the model reasons.
The #1 exam reflex"Guaranteed / mandatory / must-happen-first" ⇒ programmatic hook or prerequisite gate. "Encourage / usually / remind" ⇒ prompt. Money & identity = hooks.
Tasks 1.6 & 1.7 · Decomposition & sessions

Chaining vs. adaptive · resume vs. fork

Prompt chaining (fixed pipeline)For predictable, multi-aspect work — e.g., review each file individually, then a cross-file integration pass. Sequential & deterministic.
Dynamic decomposition (adaptive)For open-ended work — e.g., "add tests to a legacy codebase": map structure, find high-impact areas, build a prioritized plan that adapts as dependencies surface.
--resume <session-name>Continue a specific named conversation. Tell the agent which files changed since, so it re-analyzes only those.
fork_sessionBranch from a shared analysis baseline to explore divergent approaches in parallel (e.g., compare two refactors).
Fresh + summary > stale resumeWhen prior tool results are stale, starting new with a structured summary is more reliable than resuming.
Don't confuseresume = continue the same thread · fork = branch to compare options · fresh+summary = when the old context is no longer trustworthy.

D2

Tool Design & MCP Integration

Tools are how agents touch the world. This domain is about writing tools the model picks correctly, failing in ways it can recover from, and wiring MCP servers into Claude Code.

EXAM DOMAIN 218% of examMedium priority
Task 2.1 · Tool interfaces

The description is the API

DefinitionTool descriptions are the primary signal the model uses to choose a tool. Minimal or overlapping descriptions cause misrouting between similar tools. Good descriptions state input formats, example queries, edge cases, and explicit boundaries ("use this vs. that"). System-prompt wording can also create unintended tool associations.
Drawer labels in a workshopIf two drawers both say "parts," you'll open the wrong one constantly. Label them "M3 screws" and "wall anchors" and your hand goes straight to the right drawer. Tool names + descriptions are those labels.

Fixes the exam rewards

  1. Expand minimal descriptions (inputs, examples, edge cases, when-to-use) — usually the best first step.
  2. Rename to kill overlap (analyze_content → extract_web_results).
  3. Split a generic tool into purpose-specific ones (extract_data_points, summarize_content, verify_claim_against_source).
  4. Audit the system prompt for keyword-sensitive wording that overrides good descriptions.
Memory hookBad tool selection? Fix the description first — it's the cheap, high-leverage move before few-shot or routing layers.
Task 2.2 · Structured errors

Fail in a way the agent can act on

DefinitionMCP tools signal failure with the isError flag — but a generic "Operation failed" tells the agent nothing. Return structured error metadata: an errorCategory (transient / validation / business / permission), an isRetryable boolean, and a human-readable explanation. This lets the agent retry transient errors, explain business errors, and not waste retries on non-retryable ones.
A useful error vs. "computer says no""Try again in 30s" (transient), "ZIP must be 5 digits" (validation), "refunds over $500 need a manager" (business) each lead to a different next move. "Failed" leads to flailing.
TransientisRetryable: true — timeout/unavailable; retry.
ValidationBad input; fix & resend, don't blind-retry.
Businessretryable: false + friendly reason; agent explains/escalates.
Access failure ≠ empty resultA timeout needs a retry decision; "0 matches" is a successful query.
Multi-agent tie-in (D5)Subagents should recover locally from transient failures and only propagate what they can't fix — with partial results + what was attempted.
Tasks 2.3–2.5 · Distribution, tool_choice, MCP wiring & built-ins

Fewer tools, scoped right, wired cleanly

Too many tools hurts~18 tools instead of 4–5 degrades selection. Give each agent scoped access to only its role's tools; add limited cross-role tools for high-frequency needs (e.g., a verify_fact for the synthesis agent).
tool_choiceauto = may return text · any = must call some tool · {type:"tool", name:"..."} = must call that tool (force extract_metadata first, then continue).
MCP scopingProject-level .mcp.json = shared team tooling (commit it); user-level ~/.claude.json = personal/experimental. Use env-var expansion in .mcp.json so secrets aren't committed.
MCP resourcesExpose content catalogs (issue summaries, doc hierarchies, DB schemas) as resources to cut exploratory tool calls. Tools = actions; resources = readable data.
Built-in toolsGrep = search file contents; Glob = match file paths; Read/Write = whole files; Edit = targeted unique-match change → fall back to Read+Write when the anchor isn't unique.
Prefer existing MCP serversUse community servers for standard integrations (Jira); build custom only for team-specific workflows. Enrich MCP tool descriptions so the agent doesn't default to built-ins like Grep over a more capable MCP tool.
Tough Scenario (sample question)

A synthesis agent does 2–3 round-trips through the coordinator for simple fact-checks (85% of cases), adding 40% latency.

Over/under-provisionGive synthesis all web tools (violates separation of concerns) — or batch every verification (creates blocking dependencies).
Least privilegeGive synthesis a scoped verify_fact tool for the simple 85%; keep routing complex 15% through the coordinator.
Memory hookRight-size the toolbox: scope tools to the role, force order with tool_choice, share via .mcp.json, keep secrets in env vars.

Claude Code Configuration & Workflows

Bending Claude Code to a team: the CLAUDE.md hierarchy, path-scoped rules, commands & skills, plan mode, iterative refinement, and CI/CD integration.

EXAM DOMAIN 320% of examHigh priority
Tasks 3.1 & 3.3 · CLAUDE.md hierarchy & path rules

Where config lives decides who gets it

DefinitionCLAUDE.md loads in a hierarchy: user (~/.claude/CLAUDE.md, personal, not shared via git), project (.claude/CLAUDE.md or root CLAUDE.md, shared), and directory (subdir files). Use @import to keep it modular, or .claude/rules/ files with YAML paths: globs so conventions load only when editing matching files.
Office-wide vs. desk-drawer rulesProject CLAUDE.md is the posted office policy everyone follows; user-level is a sticky note on your own monitor. Put a rule on your monitor and wonder why the new hire ignores it — that's the classic bug.
Hierarchy bugNew teammate missing instructions? They were in ~/.claude/ (user) instead of project config. Move them to project scope.
@importPull in standards files per package so each CLAUDE.md stays focused.
.claude/rules/ + globspaths: ["**/*.test.tsx"] applies test conventions to files spread across the codebase — better than per-directory CLAUDE.md.
/memoryVerify which memory files are loaded when behavior is inconsistent.
Memory hookShared with the team? It must be project-scoped (committed). For conventions that span folders, reach for .claude/rules/ globs, not subdir CLAUDE.md.
Task 3.2 · Commands & skills

Slash commands & skills (and context: fork)

Commands scope.claude/commands/ = project, shared via git (everyone gets /review on clone); ~/.claude/commands/ = personal.
SkillsLive in .claude/skills/ as SKILL.md with frontmatter.
context: forkRuns the skill in an isolated sub-agent context so verbose output (codebase analysis, brainstorming) doesn't pollute the main conversation.
allowed-toolsRestrict tool access during skill execution (e.g., limit to file writes to prevent destructive actions).
argument-hintPrompts the developer for required parameters when they invoke without args.
Skill vs CLAUDE.mdSkill = on-demand, task-specific; CLAUDE.md = always-loaded universal standards. Personal skill variant? Different name in .claude/skills/ to avoid affecting teammates.
Tough Scenario (sample question)

You want a /review command available to every developer on clone/pull.

Wrong spots~/.claude/commands/ (personal only) · root CLAUDE.md (that's context, not commands) · a config.json commands array (doesn't exist).
Right answerProject .claude/commands/ — version-controlled, auto-available to the whole team.
Exam goldcontext: fork = isolate noisy skill output. allowed-tools = safety rails. argument-hint = prompt for missing args.
Tasks 3.4–3.6 · Plan mode, refinement & CI/CD

Plan vs. execute · iterate · automate

Plan modeFor large-scale, multi-file, architectural, multiple-valid-approach work (microservice split, library migration across 45+ files). Explore safely before committing.
Direct executionFor simple, well-scoped changes (one-file bug fix, add a validation check).
Explore subagentIsolate verbose discovery, return a summary — preserves main context.
Iterative refinementConcrete input/output examples beat prose; test-driven iteration (share failures); the interview pattern (let Claude ask questions first); fix interacting issues together, independent ones sequentially.
CI/CD: -p / --printNon-interactive mode — required in pipelines or the job hangs waiting for input.
--output-format json + --json-schemaMachine-parseable findings → post as inline PR comments.
CLAUDE.md in CICarries testing standards, fixtures, review criteria to the CI-invoked agent.
Independent review instanceThe session that wrote the code is worse at reviewing it — spin up a fresh instance without the generator's reasoning context.
Re-runsPass prior findings; instruct it to report only new/unaddressed issues to avoid duplicate comments.
Tough Scenario (sample question)

Restructure a monolith into microservices — dozens of files, service-boundary decisions.

WrongDive into direct execution and let boundaries "emerge" — costly rework when dependencies surface late.
RightPlan mode: explore, map dependencies, design the approach, then execute. Complexity is already known up front.
Memory hookBig/architectural ⇒ plan mode. One-file/clear ⇒ direct. In CI, always -p, and review with a fresh instance.

Prompt Engineering & Structured Output

Getting reliable, machine-parseable results: explicit criteria, few-shot, JSON-schema tool_use, validation-retry loops, batch processing, and multi-pass review.

EXAM DOMAIN 420% of examHigh priority
Tasks 4.1 & 4.2 · Explicit criteria & few-shot

Specific criteria beat "be careful"

DefinitionPrecision comes from explicit categorical criteria, not vague confidence dials. "Flag a comment only when its claimed behavior contradicts the code" works; "be conservative" or "only high-confidence findings" doesn't. Few-shot examples are the most effective way to get consistent format and judgment — 2–4 targeted examples that show reasoning for ambiguous cases generalize to novel ones.
A rubric, not "use your judgment"Tell five graders "grade fairly" and you get five results. Give them a rubric with examples and they converge. Few-shot examples are the worked answers stapled to the rubric.
False positives erode trustOne noisy category makes devs distrust the accurate ones. Temporarily disable a high-FP category while you fix it.
Define severity by exampleConcrete code per severity level → consistent classification.
Few-shot for extractionShow varied document structures (inline citations vs bibliographies) to cut empty/null/hallucinated fields.
Memory hookVague tuning ("be strict / high-confidence only") almost never wins on the exam. The answer is explicit criteria + few-shot examples.
Tasks 4.3 & 4.4 · JSON schemas & validation-retry

tool_use schemas kill syntax errors (not semantic ones)

DefinitionThe most reliable way to get schema-compliant output is tool_use with a JSON schema — it eliminates JSON syntax errors. It does not prevent semantic errors (line items that don't sum, values in the wrong field). Make fields nullable/optional when the source may lack them, so the model returns null instead of fabricating. Add enum values like "unclear" and an "other" + detail pattern for extensibility.
A fill-in form vs. a blank pageA structured form guarantees every box is filled in the right shape — but it can't stop someone writing the wrong city in the city box. That's what validation-retry is for.

Validation-retry loop

  1. Extract via tool_use; validate (e.g., Pydantic / schema).
  2. On failure, resend with the document + failed extraction + specific error.
  3. Know the limit: retries fix format/structural errors, not missing info.
  4. Self-check semantics: extract calculated_total vs stated_total, add a conflict_detected flag.
Don't confuseStrict schema = no syntax errors. It does NOT catch semantic errors. Nullable fields stop fabrication; retries can't conjure info that isn't in the source.
Tasks 4.5 & 4.6 · Batch API & multi-pass review

Batch economics & review architecture

DefinitionThe Message Batches API gives 50% cost savings with an up-to-24-hour window and no latency SLA — great for non-blocking jobs (overnight reports, weekly audits), wrong for blocking ones (pre-merge checks). It does not support multi-turn tool calling in a single request. Correlate pairs with custom_id; resubmit only failed items.
Standard post vs. courierBatch is cheap standard post — perfect for things due "by tomorrow," useless when someone's waiting at the counter. Pre-merge checks need the courier (sync API).
Multi-pass reviewSplit big reviews into per-file local passes + a cross-file integration pass to avoid attention dilution & contradictory findings.
Independent > self-reviewA second instance without the generator's context catches more than self-review or extended thinking.
Bigger context ≠ betterA larger window doesn't fix attention quality across 14 files — splitting does.
Memory hookBatch = cheap + slow + no live tools → only for latency-tolerant jobs. Blocking workflow? Sync API. Resubmit failures by custom_id.

Context Management & Reliability

Keeping agents accurate over long, multi-agent, multi-document work — context hygiene, escalation, error propagation, provenance, and human-review calibration.

EXAM DOMAIN 515% of examMedium priority
Tasks 5.1 & 5.4 · Context hygiene

Lost in the middle & the case-facts block

DefinitionModels reliably use the beginning and end of long inputs but drop the middle ("lost in the middle"). Progressive summarization quietly destroys exact numbers, dates, and customer-stated expectations. Tool results pile up tokens (40+ fields when 5 matter). Fixes: pull hard facts into a persistent case-facts block, trim tool outputs to relevant fields, and put key summaries at the start with section headers.
A whiteboard of "known facts"Long meetings blur the details. The dependable teams keep a whiteboard of locked-in numbers (order #, amount, deadline) that never gets summarized away — that's the case-facts block.
Case-facts blockExtract amounts/dates/IDs/statuses into a persistent block included every prompt, outside summarized history.
Trim tool outputsKeep only the relevant fields before they accumulate.
Big codebasesScratchpad files persist findings across context boundaries; delegate verbose exploration to subagents; /compact when context fills; crash-recovery via state manifests the coordinator reloads.
Memory hookDon't summarize away numbers. Keep a case-facts block, trim tool noise, and place critical info at the start & end — never buried mid-prompt.
Tasks 5.2 & 5.3 · Escalation & error propagation

Know when to hand off — and how to fail

Escalation triggersCustomer explicitly asks for a human · policy gap/exception (not just "complex") · can't make meaningful progress.
Honor explicit requestsIf they demand a human, escalate immediately — don't investigate first. If they're just frustrated but the issue is solvable, acknowledge & offer to resolve; escalate only if they reiterate.
Bad proxiesSentiment and self-reported confidence don't correlate with case complexity — don't escalate on them.
Multiple matchesAsk for more identifiers; never pick by heuristic.
Structured error contextFailure type + attempted query + partial results + alternatives → coordinator makes a smart recovery call.
Access failure ≠ empty resultTimeout needs a retry decision; "no matches" is a valid success.
Anti-patternsSilently suppressing errors (empty-as-success) and terminating the whole workflow on one failure are both wrong.
Local recovery firstSubagents resolve transient issues themselves; propagate only the unrecoverable, with what was tried.
Tough Scenario (sample question)

A web-search subagent times out. How should the failure reach the coordinator?

WrongGeneric "search unavailable" (hides context) · empty-result-as-success (suppresses) · kill the whole workflow.
RightReturn structured error context (type, attempted query, partial results, alternatives) so the coordinator can retry, reroute, or proceed with partial coverage.
Exam reflex"When unsure / policy silent / multiple matches" → ask or escalate, never guess. Errors should inform, not hide or detonate.
Tasks 5.5 & 5.6 · Calibration & provenance

Trust, but verify by segment & source

Aggregate metrics lie"97% overall" can hide a document type or field that performs terribly. Analyze accuracy by document type and field before automating.
Stratified samplingSample high-confidence extractions to measure real error rates & catch novel patterns.
Field-level confidenceHave the model emit per-field confidence; calibrate thresholds with a labeled validation set; route low-confidence/ambiguous items to humans.
ProvenanceRequire claim→source mappings (URL, doc name, excerpt) that survive synthesis; summarization is where attribution gets lost.
Conflicts & timeAnnotate conflicting stats with source attribution (don't pick one arbitrarily); require publication/collection dates so temporal gaps aren't read as contradictions; report coverage gaps explicitly.
Memory hookNever let a high average greenlight automation — segment by type/field. Preserve claim→source through every hop, and annotate conflicts instead of resolving them silently.

DefinitionGenerative AI creates new content (text, code, images) by learning statistical patterns from massive training data and predicting what comes next. Topics 1–3 · Models & Accessing the API

Requests, system prompts, temperature & streaming

DefinitionYou call Claude by POSTing a messages array (roles: user / assistant) to the API with an API key. A system prompt sets persona & rules; temperature (0→1) tunes randomness; streaming returns tokens as they're generated; and you can coax structured data (JSON) out for programmatic use. Conversations are multi-turn because you resend the history each call.
The model is stateless — you carry the memoryEvery API call is like meeting someone with amnesia: you must hand them the whole conversation transcript again. The "chat" feeling is an illusion you create by re-sending history.

Anatomy of a request

  1. Pick a model (Haiku/Sonnet/Opus) and set max_tokens.
  2. Optionally set a system prompt for role & rules.
  3. Send the messages array (full history for multi-turn).
  4. Read the reply; for UIs, stream it token-by-token.

Choosing a model

HaikuFastest & cheapest — high-volume, simple tasks.
SonnetBalanced workhorse — most production work.
OpusMost capable — hardest reasoning & agentic jobs.
TemperatureLow = precise/repeatable; high = creative/varied.
Memory hookThe API has no memory. Multi-turn = you mailing the whole letter-chain back every time. Forget a turn, Claude forgets it too.
Topic 4 · Prompt evaluation

Evals: prove it works before you ship

DefinitionAn eval is a test suite for prompts. You build a test dataset of inputs (often Claude-generated), run your prompt against each, and grade the outputs — either by code (deterministic checks: did it return valid JSON? contain the keyword?) or by model (an LLM judges quality against a rubric).
Unit tests for your promptsYou'd never ship code without tests. An eval is the same safety net for prompts: change the wording, re-run the suite, and see instantly whether you improved things or quietly broke them.

A typical eval workflow

  1. Define the task & success criteria.
  2. Generate a test dataset of representative inputs.
  3. Run the prompt across all cases.
  4. Grade by code (objective) or model (subjective), then iterate.
Don't confuseCode-based grading = deterministic/objective (regex, JSON valid, exact match). Model-based grading = an LLM scores fuzzy quality (tone, helpfulness).
Topic 5 · Prompt engineering techniques

Clear · Specific · Structured · Exemplified

DefinitionFour reliable levers for better outputs: Be clear and direct (plain, unambiguous instructions), Be specific (state format, length, audience, constraints), Structure with XML tags (wrap inputs/instructions in tags like <document> so Claude parses roles cleanly), and Provide examples (few-shot — show the pattern you want).
Briefing a freelancer by email"Make a logo" gets chaos. "Make a minimalist logo, navy & white, vector, for a law firm — here are two I like" gets gold. Specificity + examples shrink the guesswork.

The four techniques

Clear & directSay exactly what to do — no hinting.
SpecificPin down format, length, tone, audience.
XML tagsDelimit inputs so boundaries are unambiguous.
Examples (few-shot)Demonstrate the exact output pattern.
Memory hookClaude loves tags. Wrapping content in <context>…</context> is the single cheapest reliability upgrade you can make.
Topic 6 · Tool use with Claude

Tool use: giving Claude hands

DefinitionTool use (function calling) lets Claude invoke your functions. You describe tools as JSON schemas; when Claude wants one, it returns a tool_use block with arguments; your code runs the function and returns a tool_result; Claude continues. It never runs code itself — it asks.
A chef calling out ordersThe chef (Claude) doesn't leave the kitchen to buy groceries. They shout "I need 2 onions!" (tool_use); the runner (your code) fetches them and returns them (tool_result); the chef keeps cooking. Claude decides what; you do the doing.

The tool-use loop

  1. Send the user message + tool schemas.
  2. Claude replies with a tool_use block (name + input).
  3. Your code runs the function, returns a tool_result.
  4. Claude reads the result and answers (or calls another tool).

Built-ins & advanced moves

Multiple toolsGive Claude a toolbox; it picks the right one.
Fine-grained tool callingStream tool params as they generate.
Text editor toolBuilt-in tool to view & edit files.

Good approachDefine a get_order_status tool. Claude calls it with the order ID, your code hits the real DB, returns the truth, Claude phrases it.

Topic 7 · RAG and Agentic Search

RAG: ground answers in your documents

DefinitionRetrieval-Augmented Generation fights hallucination and stale knowledge by fetching relevant text before answering. You chunk your docs, turn chunks into embeddings (vectors), store them, and at query time retrieve the closest chunks — then hand them to Claude as context. Add BM25 (keyword) search alongside vectors for a multi-index hybrid.
Open-book examInstead of answering from memory (and bluffing), Claude flips to exactly the right pages first, then writes the answer with the book open. Retrieval = finding the page; generation = writing the answer.

The full RAG flow

  1. Chunk documents into passages.
  2. Embed each chunk & store the vectors.
  3. At query time, retrieve the most similar chunks (semantic + BM25 lexical).
  4. Stuff them into the prompt; Claude generates a grounded answer.
Don't confuseEmbeddings/semantic search = meaning ("car" matches "automobile"). BM25 = exact keywords. Best pipelines fuse both (multi-index / hybrid).
Topic 8 · Features of Claude

Prompt caching, thinking, vision, PDF & citations

DefinitionThe power features: Extended thinking (a visible reasoning scratchpad for hard problems), image & PDF support (multimodal input), Citations (answers that point back to source spans), Code execution + Files API (run code on uploaded files), and the architect's favorite — Prompt caching: cache a big stable prefix so repeat calls are far cheaper and faster.
Prompt caching = a bookmark in a huge manualWithout it, Claude re-reads the entire 50-page manual every call. With caching, it bookmarks the manual once and jumps straight to your new question — you pay full price once, then a fraction.

Rules of prompt caching

  1. Caching works on a prefix — put stable content (system, docs, tools) first.
  2. Mark it with a cache breakpoint; minimum ~1024 tokens to cache.
  3. Cache has a ~5-minute TTL, refreshed on each hit.
  4. Keep volatile content (the new question) last, after the cached block.

Feature use-cases

Extended thinkingMulti-step math, planning, tricky debugging.
Vision / PDFRead charts, scans, invoices, slide decks.
CitationsTrustworthy answers that link to the source.
CachingChatbots over a fixed knowledge base — cheap repeats.
Memory hookCache the stuff that doesn't change, put it first, keep the question last. Stable-front, volatile-back.

Topic 11 · Agents and workflows

Workflows vs. Agents — the architect's decision

DefinitionA workflow orchestrates LLM calls through predefined code paths — chaining (output to input), routing (classify, then branch), parallelization (fan-out, combine). An agent lets the model dynamically direct its own process — choosing tools, inspecting the environment, and looping until done. Workflows are predictable; agents are flexible.
Train tracks vs. a self-driving carA workflow is a train on fixed rails — reliable, same route every time. An agent is a self-driving car deciding turns from what it sees. Use rails when the route is known; use the car when it isn't.

Workflow patterns

  1. Chaining — break a task into ordered steps.
  2. Routing — classify input, send to the right handler.
  3. Parallelization — run subtasks at once, then merge.
  4. Agent — model loops with tools + environment feedback.
Tough Scenario

You're building a support bot. Tempting to make it a fully autonomous agent from day one.

Bad approachOver-engineer an open-ended agent for a task that's really "classify the ticket, route it, reply." Unpredictable, hard to debug, costly.
Good approachUse a routing workflow: it's predictable, testable, cheap. Reserve agents for genuinely open-ended tasks where steps can't be known up front.
Exam goldAnthropic's mantra: use the simplest thing that works. Workflow if the path is knowable; agent only when it isn't.

Topic 2 · Core MCP features

Sampling, Notifications & Roots

DefinitionSampling lets a server ask the client's LLM to generate text — the request flows backward, so servers stay model-agnostic. Notifications (log + progress) let a server stream status during long jobs. Roots tell a server which filesystem locations it's allowed to touch — a scoping/safety boundary.
Sampling = the contractor borrowing your phoneInstead of buying their own, the contractor (server) asks to use your phone (the client's model) to make a call. They get LLM power without owning a model or your API key.

How sampling flows

  1. Server hits a step where it needs LLM reasoning.
  2. It sends a sampling request up to the client.
  3. The client (with user oversight) runs its model.
  4. The completion flows back down to the server.
Memory hookSampling reverses the arrow: the server asks the client's model. Server stays model-free; the client (and user) keep control.
Topic 3 · Transports and communication

STDIO vs. StreamableHTTP

DefinitionMCP messages are JSON-RPC. Two transports carry them: STDIO — the server runs as a local subprocess, talking over standard in/out (great for local tools, zero network). StreamableHTTP — the server is reached over HTTP, supporting streaming and remote/multi-user deployments, where state management matters.
Intercom vs. phone lineSTDIO is an intercom to the room next door — instant, local, one-to-one. StreamableHTTP is a phone line that reaches anywhere, handles many callers, but needs you to track who's on which call (state).
Tough Scenario

You built a local STDIO server; now the team needs it hosted centrally for many users.

Bad approachForce STDIO to go remote — it's built for a local subprocess, not multi-user networking, so it doesn't scale.
Good approachSwitch to StreamableHTTP: built for remote, streaming, multi-client use — and plan session/state handling deliberately.
Exam goldSTDIO = local subprocess · StreamableHTTP = remote/networked & streamable. Underlying messages are JSON-RPC either way.

Introduction to Subagents

Delegate work to subagents — separate context windows that keep your main conversation clean, focused, and cheap.

1 topic4 lessons High · D1 anthropic.skilljar.com/introduction-to-subagents
Topic 1 · Subagents

A clean room for messy work

DefinitionA subagent is a separate Claude instance with its own context window and (optionally) its own tools and system prompt. The main agent delegates a chunk of work; the subagent does it in isolation and returns just the result — so noisy intermediate steps never pollute the main thread.
Sending a researcher to the archivesYou don't drag every dusty box back to your desk. You send a researcher (subagent) to dig through them and return with the one-page summary. Their mess stays in the archive.

How delegation works

  1. Main agent identifies a self-contained subtask.
  2. It spawns a subagent with a focused brief (& maybe specific tools).
  3. The subagent works in its own context — burning its own tokens.
  4. It returns a clean result; the main context stays lean.
Tough Scenario

A task needs reading 30 files to find one function — doing it inline floods the main context with junk.

Bad approachRead all 30 files in the main thread; now its context is clogged with irrelevant code and it loses focus on the real goal.
Good approachSend a subagent to search the 30 files and return just the file:line. Main context stays sharp; you only pay tokens for the answer.
Memory hookSubagent = a fresh context window you can throw away. Great for wide searches & noisy subtasks. Designing a tight brief is the whole skill.

AI Capabilities and Limitations

How AI actually works under the hood — four properties that explain everything Claude is great at, and everything it isn't.

6 topics14 lessons Medium · D5 anthropic.skilljar.com/ai-capabilities-and-limitations
Topics 1–5 · The four properties

Prediction · Knowledge · Memory · Steerability

DefinitionFour properties explain LLM behavior. Next-token prediction: it generates one token at a time, each conditioned on all prior text. Knowledge: facts baked in during training (with a cutoff). Working memory: the context window — its only "now." Steerability: how prompts, system messages, and examples shape its behavior. How AI gets its character comes from training + steering.
An improv actor with a great memory but no notebookThey riff one line at a time (prediction), know a lot from past roles (knowledge), only remember what's said in this scene (working memory), and take direction brilliantly (steerability).

Each property explains a real limit

PredictionWhy it can sound right yet be wrong — it predicts plausibility.
KnowledgeWhy it has a cutoff & needs RAG for fresh/private facts.
Working memoryWhy long chats "forget" — context is finite.
SteerabilityWhy system prompts & examples change everything.
Topic 6 · When properties collide

Hallucination is a feature meeting a limit

DefinitionWhen Properties Collide: the properties interact, and that's where surprises live. Next-token prediction always produces fluent text, but when knowledge is missing the result is a confident hallucination. Limited working memory plus a long task means earlier instructions fade. Understanding the collisions is what makes you safe and effective.
A GPS that never says "I don't know"It will always draw a route, even into a lake — because its job is to output a path, not to verify the road exists. Prediction without knowledge = a confident route to nowhere.
Tough Scenario

You ask for a citation on a niche topic and Claude returns a perfectly formatted but fake paper.

Bad approachTrust it because it looks authoritative — fluent formatting reads as truth. (Prediction met a knowledge gap.)
Good approachGround it: give the real sources via RAG, demand Citations, and verify. Add knowledge so prediction has something true to predict from.
Memory hookHallucination = prediction running on empty knowledge. The fix is almost always "give it the facts" (RAG + Citations), not "ask nicer."
Full-circleThis course explains why everything else in the notebook works: context is king (Ch.1), RAG grounds knowledge (Ch.6), prompts steer (Ch.5/6), and judgment stays human (the 4Ds).
