Domain 1 · 27% · The Heartbeat

The Agentic Loop

Keep cooking until the dish says "done"

An agent isn't magic — it's a loop. Send to Claude, look at one signal, act if told to, send again. The entire exam stands on this one idea, so get it bone-deep.

Fig. 1 · The loop, driven by stop_reason

How the loop actually runs

You send a request. Claude responds with a stop_reason. If it's "tool_use", the model is asking you to run a tool — so you execute it, append the result to the conversation history, and send again. If it's "end_turn", Claude is finished — you stop and show the answer. That's the whole engine.

Crucially, this is model-driven: Claude decides which tool to call next based on context. You are not hardcoding a decision tree or a fixed tool sequence — you're letting the model reason its way forward.

ANALOGY
A chef keeps cooking — taste, adjust, taste — until the dish is ready. They don't stop because they've stirred exactly 5 times. stop_reason is the "is it ready?" taste test.

The anti-patterns the exam loves to punish

  • Parsing natural language to decide when to stop ("if the reply contains 'done'…"). Fragile and wrong — use stop_reason.
  • Arbitrary iteration caps as your primary stopping mechanism. A safety net, yes; the main control, no.
  • Checking assistant text content as a completion signal. The signal is structural, not prose.

The problem: Your agent sometimes loops forever, sometimes quits early. You've been scanning the reply text for the word "complete."

Bad approach: Add more keywords to scan for. (You're now playing whack-a-mole with English.)

Good approach: Drive control flow purely on stop_reason — continue on "tool_use", terminate on "end_turn". Deterministic, language-agnostic, correct.

MEMORY HOOK
"stop_reason is the boss." The structural signal drives the loop — never the prose, never a counter, never a vibe.

Domain 1 · The Newsroom

Multi-Agent Orchestration

One editor, many reporters, hub-and-spoke

When one agent isn't enough, you build a crew: a coordinator who delegates, and specialized subagents who do the focused work. But there's a catch that trips up half the test-takers — the subagents have amnesia.

Fig. 2 · Hub-and-spoke coordination

How coordination works

The coordinator decomposes the task, decides which subagents to invoke based on query complexity, and routes all communication for observability and consistent error handling. Subagents are spawned via the Task tool — and the coordinator's allowedTools must include "Task" or it simply can't spawn anything.

The big gotcha: subagents run with isolated context. They do not inherit the coordinator's conversation history, and they share no memory between invocations. Whatever a subagent needs to know, you must put directly in its prompt — including complete findings from prior agents.

Going parallel

To run subagents at the same time, the coordinator emits multiple Task tool calls in a single response — not across separate turns. Partition the work (distinct subtopics or source types per agent) to minimize duplication, and design coordinator prompts around goals and quality criteria, not rigid step-by-step instructions, so subagents stay adaptable.

MEMORY HOOK
"Subagents have amnesia." They remember nothing you don't hand them in the prompt. Pass findings explicitly, with source metadata attached.

The problem: You research "impact of AI on creative industries." Every subagent succeeds — yet the final report covers only visual arts. The coordinator's log shows it split the topic into "digital art," "graphic design," and "photography."

Bad diagnosis: Blame the search agent's queries, or the synthesis agent's gap-detection. They all worked correctly within their assigned scope.

Right diagnosis: The coordinator's decomposition was too narrow — it never assigned music, writing, or film. Fix the decomposition and add iterative refinement loops that re-delegate when coverage has gaps.

Domain 1 · The Bouncer

Enforcement & Hooks

A gate beats a guideline when money's on the line

Prompts are persuasion. Hooks are physics. When a business rule absolutely must hold — verify identity before a refund — you don't ask nicely. You build a wall the agent literally cannot walk through.

Fig. 3 · Programmatic gate vs prompt-based hope

Two kinds of hooks

  • PostToolUse hooks intercept tool results before the model sees them — perfect for normalizing messy data (Unix timestamps, ISO 8601, numeric status codes) into one clean format.
  • Tool-call interception hooks intercept outgoing calls to enforce rules — e.g., block any refund over $500 and redirect to human escalation.

The principle that wins points

When compliance must be guaranteed — identity checks before financial operations, hard policy limits — use programmatic enforcement (hooks, prerequisite gates). Prompt instructions have a non-zero failure rate, which is unacceptable when errors cost money. Use prompts for guidance; use code for guarantees.

Structured handoffs

When escalating mid-process to a human who can't see the transcript, hand off a structured summary: customer ID, root-cause analysis, refund amount, and recommended action. Don't make the human reverse-engineer the conversation.

Straight from the practice exam · Q1
Agent skips get_customer 12% of the time → wrong refunds. The fix isn't a stronger prompt or more few-shot examples. It's a programmatic prerequisite that blocks lookup_order and process_refund until get_customer returns a verified ID. Prompts (B, C) are probabilistic; a routing classifier (D) fixes availability, not ordering.
MEMORY HOOK
"If money's on the line, use a gate — not a guideline." Deterministic compliance = hooks. Probabilistic = prompts.

Domain 1 · The Assembly Line & The Detective

Decomposition & Sessions

Chain when you know the steps, branch when you don't

Big tasks need a plan of attack. Sometimes the steps are obvious (assembly line). Sometimes you discover them as you go (detective). And once work spans days, you'll need to resume, fork, or wisely start fresh.

Fig. 4 · Fixed chaining vs adaptive decomposition + sessions

Choosing your decomposition

  • Prompt chaining for predictable, multi-aspect work: review each file individually, then run a separate cross-file integration pass.
  • Dynamic decomposition for open-ended investigation: "add comprehensive tests to a legacy codebase" → first map the structure, identify high-impact areas, then build a prioritized plan that adapts as dependencies surface.
  • Split large reviews into per-file passes plus a cross-file pass to avoid attention dilution.

Managing sessions across time

Use --resume <session-name> to continue a specific named conversation, and fork_session to spin independent branches from a shared analysis baseline (e.g., comparing two refactoring strategies). When prior tool results have gone stale — code changed since you last looked — it's more reliable to start fresh with a structured summary than to resume on outdated context. If you do resume, tell the agent exactly which files changed for targeted re-analysis.

MEMORY HOOK
"Chain when you know the steps; branch when you don't." And: stale results → fresh start with a summary beats a stale resume.

Domain 2 · 18% · The Job Posting

Designing Tool Interfaces

A tool is only as findable as its description

The model picks tools by reading their descriptions — that's the entire selection mechanism. Write vague descriptions and you'll get the wrong tool called, confidently, again and again.

Fig. 5 · Why tool selection goes wrong

What a great tool description contains

Each description should spell out the tool's purpose, input formats, example queries, edge cases, and boundaries — including when to use it versus a similar alternative. Ambiguous, overlapping descriptions (analyze_content vs analyze_document with near-identical text) cause misrouting.

Two fixes: rename and re-scope to kill overlap (analyze_content → extract_web_results with a web-specific description), and split generic tools into purpose-specific ones with clear input/output contracts. Also watch your system prompt — keyword-sensitive wording there can quietly override even well-written descriptions.

Straight from the practice exam · Q2
Agent calls get_customer for order queries; both tools have minimal descriptions. Most effective first step? Expand each tool's description with input formats, example queries, edge cases, and boundaries. It's the root cause and a low-effort, high-leverage fix. Few-shot (A) adds tokens without fixing the cause; a routing layer (C) is over-engineered; consolidation (D) is more effort than a "first step" warrants.
MEMORY HOOK
"A tool is only as findable as its description." Selection problems? Fix the words first — before reaching for few-shot or routing layers.

Domain 2 · The GPS & The Toolbox

MCP Errors & Tool Distribution

Recalculate the route; hand out small toolboxes

A good error tells the agent exactly what went wrong and whether to try again. A generic "Operation failed" is a dead end. And the more tools you pile on an agent, the worse its aim gets.

Fig. 6 · Structured errors + tool-count vs reliability

Errors that enable recovery

Use the MCP isError flag and return structured metadata: an errorCategory (transient / validation / business / permission), an isRetryable boolean, and a human-readable message. This lets the agent retry transient failures, explain business-rule violations to the customer, and stop wasting attempts on non-retryable errors. Critically, distinguish access failures (a timeout needing a retry decision) from valid empty results (a successful query that simply found nothing). Subagents should recover locally from transient blips and only propagate what they truly can't resolve — with partial results and what was attempted.

Distributing tools wisely

Too many tools degrades selection — an agent with 18 tools chooses worse than one with 4–5. Agents also misuse tools outside their specialty (a synthesis agent attempting web searches). Apply least privilege: scope each agent to its role, add only a few high-frequency cross-role helpers, and use tool_choice ("auto" / "any" / forced) to control when and what gets called.

Straight from the practice exam · Q9
Synthesis agent needs verification; 85% are simple fact-checks, 15% complex. Give it a scoped verify_fact tool for the common case, and keep delegating complex checks through the coordinator. That's least privilege. Giving it all web tools (C) over-provisions and breaks separation of concerns; batching (B) creates blocking dependencies; speculative caching (D) can't predict needs.
MEMORY HOOK
"Small toolbox, clear error map." 4–5 tools per agent, and every error says its category + whether to retry.

Domain 2 · The Plugins & The Knives

MCP Servers & Built-in Tools

Project scope = shared, secrets live in env vars

MCP servers plug external systems into Claude Code; the built-in tools are your everyday kitchen knives. Knowing where config lives — and never committing a secret — is pure exam points.

Fig. 7 · Config scopes + the built-in toolset

Wiring up MCP servers

  • Project scope (.mcp.json): shared team tooling, committed to version control.
  • User scope (~/.claude.json): personal or experimental servers, not shared.
  • Use environment-variable expansion (${GITHUB_TOKEN}) so credentials never get committed.
  • All configured servers' tools are discovered at connection time and available simultaneously.
  • Expose MCP resources as content catalogs (issue summaries, doc hierarchies, DB schemas) to cut exploratory tool calls. Prefer community servers (e.g., Jira) over custom ones for standard integrations.
  • Enhance MCP tool descriptions so the agent doesn't default to a built-in (like Grep) over a more capable MCP tool.

Picking the right built-in tool

Grep searches file contents (find all callers of a function). Glob matches file paths (**/*.test.tsx). Read/Write handle whole files; Edit makes targeted changes via unique text matching — and when the anchor text isn't unique, fall back to Read + Write. Don't read everything upfront: start with Grep to find entry points, then Read to follow imports and trace flows.

MEMORY HOOK
"Project = shared, user = solo. Secrets in env vars." And Edit choking on duplicate text → Read + Write to the rescue.

Domain 3 · 20% · The Handbook & The Memos

CLAUDE.md & Rules

Always-on vs sometimes-on, scoped by path

CLAUDE.md is your project's standing instructions — the company handbook. Path-scoped rules are department memos that appear only when you're working on the right files. Knowing which lever to pull is half this domain.

Fig. 8 · Config hierarchy + how each piece loads

The hierarchy and how to keep it sane

CLAUDE.md loads at three levels: user (~/.claude/CLAUDE.md — applies only to you, not shared via version control), project (.claude/CLAUDE.md or root), and directory (subdirectory files). Use @import to pull in external standards files and keep things modular, or split a monolith into topic files under .claude/rules/. The /memory command shows which memory files are actually loaded — your go-to for diagnosing inconsistent behavior.

Path-scoped rules and skills

.claude/rules/ files carry YAML frontmatter with glob paths (e.g., paths: ["terraform/**/*"]) so a rule loads only when you edit a matching file — ideal for conventions that span directories (test files scattered everywhere). Skills live in .claude/skills/ with SKILL.md frontmatter: context: fork runs them in an isolated subagent context (no pollution of the main chat), allowed-tools restricts access, and argument-hint prompts for missing parameters. Project-scoped commands and skills (.claude/...) are version-controlled and team-wide; ~/.claude/... variants are personal.

Practice exam · Q4
A /review command for every developer on clone/pull? Put it in .claude/commands/ — version-controlled, shared automatically. Not ~/.claude/ (personal), not CLAUDE.md, not a non-existent config.json.
Practice exam · Q6
Conventions for test files scattered across the codebase? Use .claude/rules/ with a glob like **/*.test.tsx. Directory-bound CLAUDE.md can't span dirs; skills need manual invocation.
MEMORY HOOK
"Always-on → CLAUDE.md. Sometimes-on → rules/ with a glob." Shared lives in .claude/; personal lives in ~/.claude/.

Domain 3 · The Blueprint & The Pipeline

Plan Mode, Iteration & CI/CD

Plan the big, just-do the small, and always -p in CI

Some tasks deserve a blueprint before a single line changes; others you just fix. And when Claude Code runs inside a pipeline, one missing flag will hang the whole job forever.

Fig. 9 · Plan vs direct + the CI flags that matter

Plan mode vs direct execution

Plan mode is for complex tasks: large-scale changes, architectural decisions, multi-file edits, multiple valid approaches (microservice restructuring, a library migration touching 45+ files). It enables safe exploration and design before you commit, preventing costly rework. Direct execution fits simple, well-scoped changes (a single-file bug fix with a clear stack trace). For verbose discovery, use the Explore subagent to isolate output and return summaries — protecting your context window.

Iterating well

The most effective clarifier is concrete input/output examples when prose is interpreted inconsistently. Try test-driven iteration (write tests first, then share failures), and the interview pattern (have Claude ask questions before implementing in an unfamiliar domain). Fix interacting problems in one message; fix independent ones sequentially.

Running in CI/CD

Use -p (or --print) to run non-interactively so the job doesn't hang waiting for input. Pair --output-format json with --json-schema for parseable findings you can post as inline PR comments. And remember: the same session that generated code is a weak reviewer of its own work — use an independent instance for review.

Practice exam · Q5
Monolith → microservices, dozens of files, boundary decisions? Enter plan mode to explore and design first. Direct execution risks late-discovered rework.
Practice exam · Q10
Pipeline hangs waiting for input? Add the -p flag. Not a non-existent CLAUDE_HEADLESS var or --batch flag; not a stdin hack.
MEMORY HOOK
"Plan the big, just-do the small. In CI, always -p."

Domain 4 · 20% · The Checklist

Prompting for Precision

"Be careful" does nothing; a checklist does everything

Vague adjectives — "be conservative," "high-confidence only" — don't move the needle. Specific criteria and a couple of worked examples do. This is the difference between a tool developers trust and one they mute.

Fig. 10 · Vague vs explicit, and what few-shot adds

Explicit criteria beat vague instructions

"Flag comments only when claimed behavior contradicts actual code behavior" works; "check that comments are accurate" doesn't. General hedges like "be conservative" or "only report high-confidence findings" fail to improve precision — define categorical criteria instead: which issues to report (bugs, security) versus skip (minor style, local patterns). Because high false-positive categories erode trust in the accurate ones, you can temporarily disable a noisy category while you fix its prompt, and define explicit severity levels with concrete code examples for consistent classification.

Few-shot: the most effective lever

When detailed instructions still produce inconsistent results, few-shot examples are the strongest fix. Use 2–4 targeted examples that demonstrate the exact output format and show reasoning for ambiguous cases (why one action beat a plausible alternative). They let the model generalize judgment to novel patterns rather than matching only pre-specified cases — and they sharply reduce hallucination in extraction across varied document structures.

Straight from the practice exam · Q3
Agent escalates easy cases, attempts hard ones — 55% resolution vs 80% target. Best fix? Add explicit escalation criteria with few-shot examples showing when to escalate vs resolve. Self-reported confidence (B) is poorly calibrated — the agent is already wrongly confident on hard cases. A trained classifier (C) is over-engineered; sentiment (D) doesn't track complexity.
MEMORY HOOK
"Adjectives don't move the needle; criteria and examples do." Confidence scores and sentiment are NOT reliable proxies.

Domain 4 · The Form & The Overnight Job

Structured Output & Batch

tool_use fixes syntax, not sense

A JSON schema via tool use is a form with required fields — you literally can't submit broken syntax. But you can still type wrong answers. And the Batch API is a money-saver only when nobody's waiting.

Fig. 11 · Schema → tool_use → validate-retry · batch vs sync

Guaranteeing structured output

Tool use with a JSON schema is the most reliable way to get schema-compliant output — it eliminates JSON syntax errors. But it does not prevent semantic errors (line items that don't sum, values in the wrong field). Control behavior with tool_choice: "auto" (may return text), "any" (must call some tool), or forced ({"type":"tool","name":"extract_metadata"} to run a specific extraction first). Make fields nullable/optional when the source may lack them — this stops the model from fabricating values to satisfy required fields — and add "other" + detail or "unclear" enums for extensible, ambiguous cases.

Validation, retry, and review

On a validation failure, append the specific error and retry with the original document and failed extraction. But know the limit: retries can't conjure information that's absent from the source — they only fix format/structural errors. To catch semantics, extract calculated_total alongside stated_total and flag discrepancies. For reviews, an independent instance beats self-review (the generator keeps its own reasoning bias), and large reviews go faster and cleaner as per-file passes plus a cross-file integration pass.

Batch processing

The Message Batches API gives 50% cost savings with up to a 24-hour window and no latency SLA — great for overnight reports and weekly audits, wrong for blocking pre-merge checks. Correlate request/response with custom_id, resubmit only failed items, and note it can't do multi-turn tool calling within a single request.

Practice exam · Q11
Batch both a blocking pre-merge check and an overnight report? Batch the report only; keep the pre-merge check synchronous. Batch's 24h window can't serve a blocking workflow.
Practice exam · Q12
14-file review gives inconsistent, contradictory feedback? Split into per-file passes + a cross-file integration pass. A bigger context window (C) doesn't fix attention dilution.
MEMORY HOOK
"tool_use fixes syntax, not sense. Batch the overnight, sync the blocking." Nullable fields stop fabrication.

Domain 5 · 15% · The Whiteboard

Context & Reliability

Pin the facts, route the doubts, keep the receipts

Context is a whiteboard that fills up fast — and models read the top and bottom far better than the middle. The reliable architect copies key facts somewhere permanent, escalates on the right signals, and never loses a source.

Fig. 12 · Lost-in-the-middle, case-facts block, provenance

Preserving context across long interactions

Progressive summarization quietly destroys numbers, percentages, dates, and customer-stated expectations. And the lost-in-the-middle effect means content buried in the middle of a long input gets skipped. So extract transactional facts (amounts, order IDs, statuses) into a persistent "case facts" block that rides outside the summarized history in every prompt; trim verbose tool outputs to only relevant fields before they pile up (40+ fields when you need 5); place key findings at the top of aggregated inputs; and lean on scratchpad files and /compact during long codebase sessions to fight context degradation.

Escalation, error propagation, and provenance

  • Escalate on the right triggers: an explicit request for a human (honor it immediately), a policy gap/exception, or genuine inability to progress. Sentiment and self-reported confidence are unreliable proxies for complexity. Multiple customer matches → ask for more identifiers, don't guess.
  • Propagate errors with structured context (failure type, attempted query, partial results, alternatives). Never silently suppress an error as "success," and never kill the whole workflow over one subagent failure.
  • Keep provenance: require claim-source mappings that survive synthesis; annotate conflicting statistics with their sources rather than picking one; include publication/collection dates so temporal differences aren't misread as contradictions.
  • Calibrate confidence: aggregate accuracy (97%!) can hide weak spots — use stratified sampling, field-level confidence calibrated on labeled sets, and route low-confidence or contradictory cases to human review.
Straight from the practice exam · Q8
A search subagent times out — how should that flow to the coordinator? Return structured error context: failure type, attempted query, partial results, and alternatives. A generic "search unavailable" (B) hides context; marking failure as success (C) prevents recovery; killing the whole workflow (D) is overkill.
MEMORY HOOK
"Pin the facts, route the doubts, keep the receipts." Case-facts block + right escalation triggers + claim-source mappings.

The night-before checklist

Twelve hooks for twelve chapters — skim these in the elevator to the test center.

01 · Agentic Loop

stop_reason is the boss. Continue on "tool_use", stop on "end_turn". Never parse text or rely on iteration caps.

02 · Multi-Agent

Hub-and-spoke. Subagents have amnesia — pass context explicitly. Parallel = multiple Task calls in one response. allowedTools must include "Task".

03 · Hooks

Money on the line → gate, not guideline. Prerequisite gates + PostToolUse hooks for deterministic compliance.

04 · Decomposition

Chain when you know the steps; branch when you don't. Stale results → fresh start with summary.

05 · Tool Interfaces

Selection = descriptions. Fix the words first. Split generic tools; rename to kill overlap.

06 · Errors & Tools

Structured errors (category + isRetryable). 4–5 tools beats 18. Least privilege + tool_choice.

07 · MCP & Built-in

Project = shared, user = solo. Secrets in env vars. Edit fails on dupes → Read + Write.

08 · CLAUDE.md

Always-on → CLAUDE.md; sometimes-on → rules/ with a glob. Commands/skills: .claude/ shared, ~/.claude/ personal.

09 · Plan & CI

Plan the big, just-do the small. In CI always -p; --output-format json for parseable results.

10 · Precision

Criteria & examples, not adjectives. Confidence scores & sentiment are unreliable proxies.

11 · Structured & Batch

tool_use fixes syntax, not sense. Nullable fields stop fabrication. Batch overnight, sync blocking.

12 · Context

Pin facts (case-facts block), beat lost-in-the-middle, keep claim-source receipts, route doubts to humans.

★ The one mega-pattern behind half the questions

  • Need a guarantee? Use code (hooks, prerequisite gates), never a prompt.
  • Tool picked wrong? Fix the description first — before few-shot or routing layers.
  • Escalation/precision off? Explicit criteria + few-shot. Not confidence scores, not sentiment.
  • Loop misbehaving? Drive it on stop_reason, not on parsed text or counters.
  • Reviewing generated code? An independent instance beats self-review.
  • Cost vs latency? Batch for non-blocking only; synchronous for anything that blocks.
  • Big architectural change? Plan mode. Small scoped fix? Direct execution.
  • Subagent failed? Propagate structured error context; never suppress or nuke the workflow.
  • Distractors are usually over-engineered (train a classifier, add infra) or probabilistic where determinism is required. Pick the proportionate, root-cause fix.
